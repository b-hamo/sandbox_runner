# SCRP × micro_VM 통합 — 하나의 WSB에서 독립된 세 세션으로

- 기능·시험 기록 기준: 2026-11-10 17:41 KST (UTC+09:00)
- 상태: 핵심 실행 흐름 검증 · 앱 창 모드
- 환경: Windows 26200.9711 · 11/09~11/10 검증 기록
- [발표용 HTML](2026-11-10.html)

기존 Host·Manager·Runner에 micro_VM을 연결했습니다. A는 WSB, B·C는 독립 앱 창 VM에서 기존 SCRP로 작업하는 흐름을 실제 검증했습니다.

## 1. 달라진 점

- **자동 배정과 세션 격리**: 자동 배정·관리 서비스가 구성된 Host에서 WSB가 비어 있으면 WSB를, 사용 중이면 독립 앱 창 micro_VM을 배정합니다. 배정은 세션 종료까지 유지합니다.
- **기존 SCRP 기능 유지**: 각 VM의 Runner가 화면·한글 입력·Router를 처리합니다. VM별 중계와 기존 인증·검사 반출을 연결했고, 기존 혼합 반복 시험에서 TXT 24개를 분리 반출했습니다.
- **복구와 뷰어 연동**: 같은 VM에서 연결·Runner 복구를 검증했습니다. 관리 서비스와 통합 뷰어의 목록·썸네일·개별 창·새 VM·종료를 연결했습니다.

## 2. 작업 A·B·C 배정 흐름

1. **작업 A → Windows Sandbox A**: A가 먼저 시작하고 WSB가 비어 있으면 WSB를 배정합니다. 전체 바탕화면을 사용합니다.
2. **작업 B → micro_VM B**: A는 유지합니다. WSB 점유를 확인한 Manager가 B용 micro_VM을 새로 배정합니다.
3. **작업 C → micro_VM C**: A·B는 유지합니다. B와 다른 VM을 C에 배정합니다.
4. **앱 준비 후 작업**: 같은 Guest에서 필요한 앱을 확인·제공한 뒤 화면 관찰·입력·Router 요청을 처리합니다. micro_VM 통신에는 VM별 중계를 사용합니다.
5. **세션별 검사 반출**: 각 세션의 Output에서 나온 파일을 검사한 뒤 해당 세션의 저장 경로로 전달합니다.

A·B·C는 고정 우선순위가 아닌 작업 이름입니다. 실제 배정은 WSB 점유 상태로 결정하며, 동시에 들어온 요청은 조정하고 배정된 세션을 중간에 다른 VM으로 이동시키지 않습니다. 이 흐름은 micro_VM 앱 창 모드와 관리 서비스가 구성된 Host를 전제로 합니다.

점유 확인·시작 잠금·자원 한도를 적용합니다. 한도 거부나 시작 실패를 이유로 기존 세션을 강제 종료하지 않습니다. 자원 한도 거부 시험과 장시간 실제 물리 메모리 고갈 시험은 다르며, 후자는 완료 증거가 없습니다.

## 3. 확인한 화면

발표용 HTML에 실제 혼합 시험의 B·C 화면을 포함했습니다.

- **B 화면**: WSB A를 유지하며 SCRP로 앱 창을 확인하고 마우스 클릭·한글 입력을 수행했습니다.
- **C 화면**: B와 다른 VM의 앱 창에 독립적으로 입력했습니다. 동일한 이름의 파일도 세션별 내용·해시·저장 경로를 구분했습니다.

화면 캡처는 당시 시험 기록이며, 현재 실행 중인 VM의 실시간 화면은 아닙니다.

## 4. micro_VM은 어떻게 켜지고 보이나요?

### 시작 흐름

**새 작업 요청 → 독립 VM 시작 → SCRP 준비 확인 → 앱 준비·실행 → 화면 보기·작업**

1. Host가 작업 요청을 전달하고 Manager가 WSB 점유를 확인합니다.
2. WSB가 사용 중이면 VM 관리 서비스가 새 micro_VM을 생성합니다. 작업의 세션과 VM ID·소유권을 연결합니다.
3. Guest Agent 준비 상태를 확인하고 VM별 통신 중계와 Runner를 연결합니다. 인증·상태 동기화 이후 SCRP READY를 확인합니다.
4. app_prepare로 필요한 앱을 준비한 뒤 같은 VM 안에서 실행합니다. Runner는 앱 창 모드로 화면과 입력을 처리합니다.
5. SCRP로 화면을 관찰하고 클릭·키보드·한글 입력을 전달합니다. 사람은 통합 뷰어에서 해당 VM의 화면을 볼 수 있습니다.

VM 생성, SCRP READY, 앱 준비, 실제 실행 완료는 별도 판정입니다. PREPARED는 파일 준비 결과이며 앱 실행 성공을 뜻하지 않습니다.

### 프로그램은 VM 안에서 실행합니다

메모장이나 작업용 프로그램의 프로세스와 파일은 해당 VM에 있습니다. Host에는 그 화면을 보여 주는 뷰어를 열 수 있습니다. B와 C는 서로 다른 격리 환경이므로, 앱 창만 보이더라도 같은 Windows 환경에서 프로그램 두 개를 실행하는 구조는 아닙니다.

### 바탕화면 대신 앱 창을 표시합니다

A는 Windows 바탕화면 전체를 사용합니다. B·C는 작업 프로그램 창을 사용하며 시작 메뉴·작업 표시줄·바탕화면 자체를 조작하는 모드는 아닙니다. Win+R 키 조합은 Runner의 전용 실행창을 엽니다. Windows 기본 실행창을 제공하는 전체 바탕화면 모드와는 구분됩니다.

### 화면을 보고 클릭·한글 입력을 전달합니다

Runner가 해당 세션의 앱 창을 캡처하고 마우스·키보드·한글 입력을 그 창으로 전달합니다. B의 입력과 C의 입력은 각 VM 안에서 처리됩니다. 현재 반출 정책이 허용하는 UTF-8 TXT를 각 Output에서 받아 Defender 검사 후 해당 세션 경로로 전달합니다. 임의 형식 파일의 반출까지 검증한 것은 아닙니다.

### 통합 뷰어에서 B·C를 열 수 있습니다

VM은 뷰어 없이도 계속 실행됩니다. 관리 서비스 연동이 적용된 통합 뷰어에서 해당 서비스가 관리하는 B·C의 목록·썸네일과 개별 창을 열고, 새 VM 생성·종료를 요청할 수 있습니다. 뷰어 창을 닫아도 VM과 작업은 유지됩니다. VM을 끝내려면 별도의 ‘끄기’ 동작으로 해당 VM을 종료합니다.

### 필요한 앱을 준비한 뒤 실행합니다

Agent가 작업에 필요한 앱을 정하고 app_prepare를 호출합니다. Manager는 알려진 Guest 실행 경로를 먼저 확인하고, 없으면 지원 목록의 Host 설치본을 PATH·App Paths·등록 경로에서 찾습니다. 언어 런타임은 세션별 ZIP으로 전달하고 Guest에서 ZIP 및 개별 파일 해시를 검증합니다. 메모장은 exe·언어 리소스를 제공합니다. Host에서 작업 앱을 실행하지 않습니다.

지원 목록은 메모장·cmd·PowerShell과 python/git/gcc/node/go/java/zig/dotnet/ruby/php입니다. 모든 앱을 무인 설치하는 엔진은 아닙니다. 설치본이 없거나 지원 밖 앱이면 NEEDS_INSTALL/UNSUPPORTED로 안내하며, Agent는 공식 설치 파일을 inbox로 받아 같은 Guest에서 설치·확인합니다. UNKNOWN/FAILED나 불확실한 실행은 자동 재시도하지 않습니다.
